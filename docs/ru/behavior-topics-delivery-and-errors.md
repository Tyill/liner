## Топики

### Исходный топик (собственный топик клиента)

При создании вы передаёте **строку топика** и **TCP-адрес привязки** (`localhost`). После успешного **`run`** клиент **регистрируется** в общем хранилище: другие процессы узнают, *«этот топик обслуживается по этому TCP-адресу под этим `unique_name`»*.

В каталог пишется **published**-адрес:

- по умолчанию — bound listen address после TCP bind; либо
- опциональный **advertise**-адрес, если до `run` вызвали `set_advertise_addr` (см. [using-the-api.md](using-the-api.md)).

Этот топик — **исходный топик** клиента. API **запрещает** отправку на него или подписку на него как на удалённого пира — такие вызовы завершаются с **`LNR_ERR_SELF_TOPIC`** (и строкой в логе).

### Целевые топики и адреса

**`send_to(topic, …)`** и **`send_all(topic, …)`** используют `topic` как **логическое имя**. Клиент ищет **TCP-адреса**, зарегистрированные для этого топика в хранилище.

- Если **адресов нет**, отправка не удаётся с **`LNR_ERR_NO_ADDR`** («not found addr for topic …»).
- Если **несколько адресов** (несколько клиентов с одним именем топика), **`send_to`** на каждый вызов выбирает **один адрес** по **round-robin** по кэшированному списку. **`send_all`** отправляет тот же payload **по одному разу на каждый зарегистрированный адрес**.

Клиент **кэширует** адреса после первого успешного поиска. Пока пиры работают, **внутренний канал** (`__#internal_channel`) обновляет кэш при connect, disconnect, subscribe и unsubscribe (см. [using-the-api.md](using-the-api.md)).

Вызывайте **`refresh_address_topic(topic)`**, когда нужно принудительно перечитать store — например после смены порта без корректного disconnect, при подписке до `run` или если отправитель не работал в момент регистрации пира.

Для операторского просмотра без отправки используйте **`list_addresses(topic)`** (каталог store как пары `(addr, unique_name)`).

### Внутренний канал (обнаружение пиров)

При **`run`** каждый клиент автоматически подписывается на **`__#internal_channel`**. Библиотека обменивается JSON-событиями между пирами и обновляет кэш адресов **без** вызова прикладного колбэка приёма. В типичном случае отправителю не нужен ручной **`refresh_address_topic`** после **`run`** или **`subscribe`** пира в рантайме. Крайние случаи — в [using-the-api.md](using-the-api.md).

Публично подписаться или отписаться от `__#internal_channel` нельзя (`LNR_ERR_INTERNAL_TOPIC`).

### Подписки (сторона приёма)

**`subscribe(topic)`** регистрирует интерес получать **прикладные полезные нагрузки**, чьи **метаданные по проводу** относятся к внутреннему **ключу топика** этого имени. В колбэк приёма попадают только топики, на которые вы подписались; остальные отбрасываются (с отладочным сообщением при включённом `liner_debug`). **`unsubscribe`** снимает эту привязку.

Обычно **`subscribe`** вызывают для топиков, которые хотите слушать **дополнительно** к исходному топику. Подписки можно зарегистрировать **до** или **после** **`run`**; если до — они применяются при старте listener.

## Доставка

### Транспорт

После того как маршрутизация разрешила **TCP-адрес**, встроенный поток **sender** открывает **обычное TCP**-соединение к **listener** пира и передаёт кадрированные сообщения. **TLS** в самой библиотеке **нет** (см. [security-defaults.md](security-defaults.md)).

### At-least-once и best-effort

API отправки экспортируют **`at_least_once_delivery`** (C: `BOOL`).

- При **включении** стек может **сохранять** ещё не доставленные сообщения и **повторять** после переподключений, используя **номера сообщений** по каналу и сохранённые позиции **ack**.
- При **выключении** отправки **best-effort**: при сбоях или офлайне пира данные могут **теряться** без записи в хранилище.

Точные правила, таймеры и дедупликация — в [offline-delivery-and-message-numbers.md](offline-delivery-and-message-numbers.md).

Чтобы узнать, сколько офлайн-блобов сейчас лежит в store у этого sender, используйте **`pending_count`** / `lnr_pending_count` (глубина может отставать, пока не сбросятся in-memory очереди).

### Упорядочивание

Библиотека стремится к **FIFO на логический канал отправитель–получатель** (`connection_key`) с учётом сбоев и повторов. **Глобального** полного порядка по всем топикам или всем клиентам **нет**.

### Контракт колбэка

Колбэк приёма получает **указатели, действительные только на время вызова**; скопируйте байты, если они нужны позже (см. [using-the-api.md](using-the-api.md)).

## Ошибки (поведенческое резюме)

- **Создание:** если хранилище не открылось или параметры неверны, в Rust — **`None`**, в C — **`NULL`**. При простом сбое открытия stderr у части Rust-конструкторов может быть пуст (см. [errors-and-logging.md](errors-and-logging.md)).
- **`run`:** возвращает **`false`** с кодом last-error, когда:
  - сбой bind/resolve → **`LNR_ERR_BIND`**
  - сбой регистрации в каталоге → **`LNR_ERR_STORE`**
  - сбой старта listener после bind → **`LNR_ERR_STARTUP`** (без паники процесса)
  - Возвращает **`true`**, если клиент **уже** был в running (идемпотентно, **`LNR_OK`**).
  Подробности: [store-startup-failure-semantics.md](store-startup-failure-semantics.md).
- **`stop`:** снимает регистрацию, дожидается потоков, очищает `published_addr`, сохраняет `bound_listen_addr`. Идемпотентно. После stop снова можно `clear_*` и свежий `run`.
- **Отправка / subscribe / refresh / clear / advertise:** **`false`** при ошибках валидации или store; выставляют **`lnr_last_error_code`**; детали обычно в **stderr** или в процессно-глобальном **log hook**.
- **Status callback** (`lnr_set_status_cb`): асинхронные peer up/down (только связанные топики) и фоновые сбои route/store/send. **Не** заменяет синхронные коды возврата.
- **Очистка данных:** **`clear_stored_messages`** и **`clear_addresses_of_topic`** успешны только когда клиент **не** running (иначе **`LNR_ERR_CLEAR_WHILE_RUNNING`**).

Полная матрица (Rust `Client`, `Liner`, C, poison mutex) — в [errors-and-logging.md](errors-and-logging.md).

## Краткая ментальная модель

1. **Хранилище** = общая телефонная книга: топик → TCP-адреса + метаданные для офлайн-очередей.
2. **Bind** = где слушает этот процесс; **published / advertise** = куда звонят пиры.
3. **Исходный топик** = ваше опубликованное имя в этой книге.
4. **`send_to` / `send_all`** = поиск пиров по строке топика, затем TCP + опциональная персистентность.
5. **`subscribe`** = какие входящие логические топики принимает ваш колбэк.
6. **Ошибки** = синхронный **boolean / null** + **код last_error** + **stderr/log hook**; асинхронные peer/route — опционально через **status callback**.
