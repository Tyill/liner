# Офлайн-доставка, переподключения и номера сообщений

Описывается **поведение во время работы** в потоках sender и listener. Константы лежат в `src/settings.rs` (ищите там, если значения изменятся).

## Область: «минимум один раз» и best-effort

Персистентность в хранилище (Redis или SQLite) для отключённых пиров относится только к сообщениям, отправленным с **`at_least_once_delivery == true`**.

Если **`at_least_once_delivery` — false**, стек не считает такие сообщения долговечными: при сбое TCP или пока пир недоступен, они могут быть отброшены и **не** записываются в хранилище путём сохранения sender’а.

## Что происходит, когда пир (listener) недоступен или TCP падает

**Со стороны sender** (фоновый поток в `sender.rs`):

1. **Неудача TCP connect** (`TcpStream::connect` в `append_streams`): сообщения в очереди для этого логического соединения передаются в `save_messages_from_sender` в хранилище **только** для сообщений с **`at_least_once_delivery`** и с **`number_mess` строго больше**, чем последний **подтверждённый listener’ом** номер из хранилища (`get_last_mess_number_for_sender`). Остальные сообщения освобождаются в памяти.

2. **Обрыв TCP во время записи** (`write_stream`): сообщения, которые не были успешно записаны, но всё ещё «впереди» подтверждения listener’а в хранилище и помечены at-least-once, возвращаются в очередь в памяти (или обрабатываются при разборе потока — те же правила персистентности при закрытии).

3. **Разбор потока** (`check_streams_close`): оставшиеся в очереди сообщения для этого соединения проходят тот же фильтр **`save_mess_to_db`** перед добавлением в очередь соединения в хранилище.

4. **Остановка sender’а** (`close_streams`): сначала ждёт текущие записи (`write_stream` держит взятые из очереди сообщения до своего завершения); запись, заблокированная на зависшем пире, обрывается закрытием сокета через **`SENDER_CLOSE_WAIT_MS`** (сейчас **1000 ms**). Затем неподтверждённые и очередные сообщения проходят тот же фильтр в хранилище.

Для трафика **at-least-once** данные, которые **не** получили подтверждение listener’а, могут пережить **отключения на уровне процесса** в **бэкенд-хранилище**, а не только в RAM.

**При переподключении** успешный `TcpStream::connect` вызывает **`load_messages_for_sender`**: sender загружает персистентную очередь из хранилища и **сливает** её с тем, что ещё в памяти для этого соединения, затем продолжает отправку.

## Как часто sender повторяет TCP

Каждые **`CHECK_AVAILABLE_STREAM_TIMEOUT_MS`** (сейчас **10 000 ms**) поток sender решает, что нужно снова вызвать **`append_streams`** (если раньше не сработал флаг **нового адреса**). Пока адрес недостижим, он остаётся во внутреннем списке повторов; каждый цикл снова пытается **`TcpStream::connect`**.

То есть «пробовать снова примерно каждые 10 секунд» верно для **попыток переподключения**, с поправкой на планирование и короткие wait/sleep в том же цикле.

## Как listener избегает двойной доставки (идемпотентность)

Каждому логическому TCP-потоку от sender соответствует **`connection_key`**. Внутри этого канала каждое полезное сообщение несёт монотонно растущий **`number_mess`**, назначенный sender’ом при создании сообщения.

**На listener’е**, при чтении с провода (`read_conn`):

- Listener держит курсор повторов на **слот** (слот один на `connection_key`, общий для всех его TCP): наибольший номер, принятый с любого из них. При привязке нового TCP курсор поднимается до сохранённого ack (**`get_last_mess_number_for_listener`**, читается из хранилища каждый раз) — рестартовавший listener стартует с правильной базы, а быстрый reconnect не доставляет повторно принятое, но ещё не сброшенное (ack отстаёт до ~1 с).
- Входящее сообщение **принимается** только если **`mess.number_mess > cursor`**. Иначе оно **отбрасывается** (освобождается без вызова колбэка приёма). Внутренние события subscribe/unsubscribe фильтр обходят.

Поэтому **повторы или дубликаты с тем же или меньшим номером не могут быть доставлены приложению дважды**, в том числе переотправка по новому TCP наперегонки с хвостом старого. Новая работа появляется только когда sender использует **строго больший** `number_mess`. Best-effort сообщение (без at-least-once) из хвоста старого TCP отбрасывается, если новый TCP уже доставил больший номер.

### Сброс хранилища sender’а (`clear_stored_messages`)

После **`clear_stored_messages`** sender нумерует заново от сохранённого ack (обычно с 1). Listener замечает это на общем хранилище:

- запись ack — compare-and-set: **`set_last_mess_number_from_listener(key, prev, val)`** пишет, только пока в хранилище `>= prev` (последнее сохранённое этим listener’ом; нет строки — считается 0), и не воскрешает очищенный ack; неудачная запись помечает слот;
- когда к слоту привязывается новый TCP, а сохранённый ack ниже сохранённого listener’ом (или слот помечен), слот перезапускается от сохранённого ack: курсор и счётчики опускаются, остальные TCP слота закрываются, очередь сбрасывается, а пачки, уже взятые потоком приёма, ack больше не двигают (эпоха слота).

Не обнаруживается: clear до первого сохранения ack этим listener’ом по слоту и **изолированные файлы SQLite** (sender чистит свой файл, ack listener’а — в другом). Там чистить обе стороны.

## Слоты accept на listener (привязка индекса)

На **listener** каждый принятый пир живёт под одним индексом `ix`, общим для параллельных векторов в `src/listener.rs`:

- `senders[ix]` — `connection_key`, `last_mess_num*`, эпоха  
- `mempools[ix]` — mempool этого пира  
- `messages[ix]` — очередь в receive callback  
- `Slots::cursor[ix]` — курсор повторов (поток stream)  

Новый TCP привязывается к слоту по **`connection_key` из заголовка первого кадра** (sender подключается с эфемерного порта, адрес ничего не говорит). Карта **`connection_key → ix`** живёт всё время listener’а; закрытие TCP убирает только это соединение. Reconnect занимает тот же слот, старый TCP дочитывается до EOF рядом с новым. **Нельзя** отдавать `ix` **другому** ключу — смешаются mempool и ACK.

Новые ключи всегда **дописывают** слот (`push`). Не «оптимизировать» общим free-list между пирами.

## Как sender и listener синхронизируются с хранилищем

- **Listener** периодически сохраняет в хранилище наибольший принятый **`last_mess_num`** (**`set_last_mess_number_from_listener`**), с порогом **`UPDATE_LAST_MESS_NUMBER_TIMEOUT_MS`** (сейчас **1000 ms**) на пути приёма — то есть подтверждения сбрасываются в БД примерно раз в секунду при нормальном тайминге, а не на каждое сообщение.

- **Sender** периодически вызывает **`get_last_mess_number_for_sender`** (тот же ключ), чтобы согласовать очереди в памяти с тем, что listener подтвердил, и **выбросить** из RAM сообщения, уже полностью подтверждённые (см. `update_last_mess_number`).

Вместе **`number_mess`** и сохранённый **последний подтверждённый номер на `connection_key`** определяют, что можно переотправить после сбоя и что listener должен игнорировать как уже обработанное.

### SQLite: один файл на процесс

**`get_last_mess_number_for_sender`** и **`set_last_mess_number_from_listener`** должны попадать в **одно и то же** бэкенд-хранилище для логического канала, если вы рассчитываете на at-least-once **без** бесконечного роста очереди sender’а: listener пишет ack, sender читает их со своей периодичностью. Если у каждого пира **свой путь `.sqlite`**, listener обновляет **только свой** файл; sender этих строк не видит — для отправок в такой схеме используйте **`at_least_once_delivery == false`**, либо перейдите на **один общий файл SQLite** (или Redis) для общих счётчиков и очередей.

## Практическое резюме

| Тема | Поведение |
|------|-----------|
| Listener офлайн / TCP down (at-least-once) | Неподтверждённые сообщения могут **сохраняться в Redis/SQLite**; sender **повторяет TCP ~каждые 10 с**; при успехе **загружает очередь** из хранилища и отправляет. |
| Отправки best-effort | **Нет** гарантии персистентности при обрывах. |
| Дубликаты по проводу | **Подавляются** на listener’е, если `number_mess` не больше последнего принятого для `connection_key` (по всем его TCP). |
| Индекс accept на listener | Sticky **`connection_key → ix`** из заголовка первого кадра; не переиспользовать `ix` для другого ключа (mempool / ACK). |
| `clear_stored_messages` у sender’а | Обнаруживается на общем хранилище (compare-and-set ack); слот перезапускается от сохранённого ack. С изолированными файлами SQLite — нет. |
| Тайминг ack | Listener сбрасывает ack в хранилище с шагом **~1 с** (`UPDATE_LAST_MESS_NUMBER_TIMEOUT_MS`). |
| Изолированный SQLite (разный путь у процессов) | **Не** используйте **`at_least_once_delivery == true`** для межпировых отправок, если не готовы к неограниченному RAM / рассинхрону ack; используйте **`false`** или **общий** файл каталога. |

## Проверка глубины очереди через API

**`lnr_pending_count` / `Client::pending_count`** суммирует офлайн-блобы для **этой идентичности sender’а**, обходя сохранённых listener’ов → `connection_key` → длину очереди в хранилище.

- Возвращает **`0`**, если ничего не ожидает.
- Глубина может **отставать**, пока сообщения at-least-once ещё только в очередях sender’а в памяти. После потери пира или **`stop`** (который сбрасывает через teardown sender’а) представление в store обычно догоняет.
- Детали и коды ошибок: [using-the-api.md](using-the-api.md), [errors-and-logging.md](errors-and-logging.md).
